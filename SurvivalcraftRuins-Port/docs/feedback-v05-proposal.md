# 玩家反馈改进方案（v0.5 → v0.7 路线）

> **状态：已全部实现并随 v0.5.0 发布**（2026-08-08）。
> 下面的方案原文保留作为设计记录；实际落地情况与差异见文末「实现记录」一节。

对应反馈三条：① 遗迹太密；② 按遗迹大小配守卫；③ 想要沉船/海底神殿/丛林神庙/沙漠神殿。
本文只做方案与可行性核对，不含代码改动。

## 一、密度：现状确实过密，实测算得出来

`StructureRegistry` 里每个槽位是「每 `GridChunks×16` 见方的格子掷一次 `Chance`」。
按 `期望个数/km² = Chance / (GridChunks×16)²  × 10⁶` 算：

| 槽位 | 格子 | 概率 | 个/km² | 备注 |
|---|---|---|---|---|
| small（营地/摊位/神龛/许愿井） | 112 m | 0.60 | **47.8** | 单槽就占了全部陆地结构的一半 |
| coast_hut | 160 m | 0.50 | 19.5 | |
| homestead | 176 m | 0.50 | 16.1 | |
| den | 208 m | 0.50 | 11.6 | |
| mine / tower | 224 m | 0.50 | 10.0 ×2 | |
| shipwreck | 256 m | 0.45 | 6.9 | |
| ocean_ship | 288 m | 0.45 | 5.4 | |
| lighthouse | 320 m | 0.50 | 4.9 | |
| grand / sky | 384 m | 0.45 | 3.1 ×2 | |

陆地槽位合计 ≈ **98 个/km²**，泊松分布下「最近邻平均距离 ≈ 0.5/√λ」= **约 50 格**。
也就是说平地上平均每走 50 格就该撞见一个遗迹 —— 玩家说「隔几步一个」是准确的。
作为参照，MC 原版全部结构加起来大约 10 个/km²，我们是它的 ~10 倍。

还有两个放大观感的因素：

1. **同槽位相邻格子会贴在一起**。`ComputeInstance` 把原点在整个格子内均匀抖动
   （`rangeX = cellSpan - sizeX - 2`），两个相邻格子的实例可以刚好各自贴着共同边界，
   实际间距接近 0。现在只有「跨槽位重叠抑制」，没有任何**最小间距**约束。
2. **小结构变体多**（营地/摊位/神龛/许愿井 4 选 1），但槽位密度最高，玩家最常看到的就是它们。

### 建议改法

**(a) 重新标定网格**（优先改 `GridChunks`，不要靠压 `Chance`——压概率会让空格子变多、变体更单调）：

| 槽位 | 现 GridChunks/Chance | 建议 | 新个/km² |
|---|---|---|---|
| small | 7 / 0.60 | **14 / 0.50** | 10.0（原 47.8） |
| homestead | 11 / 0.50 | **18 / 0.45** | 5.4 |
| coast_hut | 10 / 0.50 | **16 / 0.50** | 7.6 |
| tower | 14 / 0.50 | **20 / 0.50** | 4.9 |
| den | 13 / 0.50 | **22 / 0.45** | 3.6 |
| mine | 14 / 0.50 | **22 / 0.45** | 3.6 |
| shipwreck | 16 / 0.45 | **24 / 0.50** | 3.4 |
| lighthouse | 20 / 0.50 | **28 / 0.50** | 2.5 |
| ocean_ship | 18 / 0.45 | **28 / 0.45** | 2.2 |
| grand | 24 / 0.45 | **40 / 0.50** | 1.2 |
| sky | 24 / 0.45 | **40 / 0.45** | 1.1 |

陆地合计 98 → **29 个/km²**，最近邻平均 ≈ **93 格**（再叠加地形/坡度/海岸筛选被否掉的候选，实际观感会更稀）。
大型结构（斗兽场、天空堡垒）从 ~570 格一遇变成 ~900 格一遇，配得上它们的体量。

**(b) 加最小间距，两种手段配合，都不破坏确定性：**

- **同槽位**：把原点抖动限制在格子中央 50%（`rangeX = (cellSpan - sizeX)/2`），
  相邻格子实例之间就有 `≥ 0.25×cellSpan` 的硬间隔，零额外计算、无递归风险。
- **跨槽位**：把现有的重叠抑制循环从「AABB 相交」升级成「中心距 < max(rA, rB) 则抑制」，
  每个 def 给一个 `SeparationRadius`（大结构 120、中 64、小 40）。
  这个循环只查**严格更高优先级**的 def，无环、可并行、结果确定；
  只需把邻域搜索范围从 `MaxFootprint` 扩到 `MaxFootprint + MaxSeparation`。
  ⚠️ 千万别让同 def 互查抑制结果——那会无限递归；同 def 用上面的中央抖动解决。

**(c) 做成可调**：`ModLoader` 有 `SaveSettings/LoadSettings(XElement)` 钩子，可以出
「遗迹密度：稀疏 0.5× / 标准 1× / 密集 2×（≈现状）」三档，让口味不同的玩家自己选。

**(d) 老存档的坑（重要）**：结构只写进「新生成的区块」。改了密度后，老世界的新探索区
会与已探索区参数不一致，跨在边界上的旧结构可能只剩写好的那半边、剩下半边永远不会补上。
建议**首次绑定世界时把密度参数固化写进 `SurvivalcraftRuins.json`**（带版本号），
老世界继续用老参数，只有新世界吃新默认值。这样升级零事故。

## 二、守卫：机制已经有了，缺的是「覆盖率 + 按体量配额」

现状盘点（`StructureRegistry` 里只有 4 个变体带 `Ambush`）：

| 变体 | 箱子 | 守卫 |
|---|---|---|
| **sky_fortress** | **16（含 4 个金库箱：钻石/火枪/钻石砍刀）** | **无** ← 全模组最肥，零风险 |
| bathhouse | 18 | 无 |
| galley | 11 | 无 |
| windmill | 16 | 无 |
| shipwreck | 3（含火枪） | 无 |
| watchtower / 各类小屋 / 沉船 / 灯塔 | 1~3 | 无 |
| coliseum | 8 | Lion 1~2 × **12 个埋伏点** = 最多 24 只 |
| ruined_temple | 8 | Jaguar 2~3 × N 点 |
| werewolf_den | 3 | Wolf_Gray 4~6 |
| mine | 2 | Hyena 2~3 |

问题是两头都不对：最肥的天空堡垒完全没人守，斗兽场却可能刷 24 只狮子。
根因是守卫数量绑在**模板里的埋伏标记个数**上，而不是结构的价值/体量。

### 建议：把 `AmbushSpec` 升级成「守卫预算制」`GuardSpec`

```
GuardSpec {
    string[] Creatures;      // 该结构的守卫池
    float PerChest;          // 每个箱子折算多少守卫
    int MinTotal, MaxTotal;  // 总量夹逼，防止斗兽场刷 24 只
    float TriggerRadius;
    bool RequiresSupernatural;  // Werewolf 之类，需世界开启超自然生物
    bool Aquatic;               // 生成点找水格而不是空气格
}
```

总数 `= clamp(round(箱子数 × PerChest + 体量系数), MinTotal, MaxTotal)`，
再把这些名额**摊到已有的埋伏标记 / 派生守卫点**上，而不是「每个标记刷一窝」。

分档建议（生物名都在 `Database.xml` 里核对过存在）：

| 档 | 守卫池 | 适用 |
|---|---|---|
| T0 无 | — | 猎人营地、集市摊位、许愿井、渔屋、神龛（保留「白捡的小惊喜」，不然探索太累） |
| T1 轻 1~2 | `Wolf_Coyote` `Hyena` | 瞭望塔、草原废屋、蘑菇屋、树屋、飞艇 |
| T2 中 3~5 | `Jaguar` `Leopard` `Bear_Black` | 废弃矿井（井下）、风车地窖、澡堂 |
| T3 重 5~8 | `Lion` `Tiger` `Bear_Brown` `Rhino` | 斗兽场、废弃神庙 |
| T4 精英 8~12 | `Tiger_White` `Werewolf`(直接生成) + T3 | **天空堡垒**（分层：金库层最强）、狼人巢穴 |
| 水下 | `Shark_Bull` `Shark_Tiger` `Barracuda` `Piranha` | 沉船、搁浅船、海底神殿 |

**分层触发**同样值得做：天空堡垒不该一进门刷 12 只，而是每层/每个金库各自一个触发半径 8 的守卫组，
越靠近金库越硬。现有 `AmbushState` 是按标记逐个持久化的，天然支持这个。

### 实现时必须处理的 4 个技术点

1. **程序化 builder 没有埋伏标记**。`LighthouseBuilder` / `MineBuilder` / `ShipwreckBuilder` /
   `CampBuilder` / `ColorfulBuilders` 都不产 `AmbushMarker`，所以它们现在给不了守卫。
   最省事的做法：在 `WorldState.WriteInstancePart` 里**按箱子位置自动派生守卫点**
   （取箱子附近可站立/可游动的格子），这样所有结构立刻都能配守卫，模板里的显式标记仍然优先。
2. **`FindSpawnY` 只找空气格**（`RuinsRuntime.cs:345`）。鲨鱼/梭鱼放到空气里会搁浅，
   水下守卫要改成找水格。
3. **AutoDespawn 行为**：`Database.xml` 里生物模板默认 `AutoDespawn=True`，
   `SubsystemSpawn.DespawnChunks` 在玩家离开 **52 格**外时把守卫收回成 `SpawnEntityData`，
   回来会**原地重新生成**。好处是宝箱不会长期无人看守；副作用是「打伤了跑开再回来，守卫满血复活」。
   要避免就在生成时把 `AutoDespawn` 设 false（代价：守卫永久占实体数）。这一条建议实测后再定。
4. **尊重世界设置**：`WorldSettings.AreSupernaturalCreaturesEnabled`（Werewolf 必须 gating）、
   `GameMode`（Harmless/冒险模式下降档或关闭）。再加一个「守卫强度：关/少/标准/多」设置项。

## 三、新结构：沉船已有，另外三个可行且 SC 元件齐全

先澄清一点：**沉船其实已经做了**（`shipwreck` 槽位，`ShipwreckBuilder`，海底 4~14 深）。
玩家没遇到多半是因为它只在合适水深生成、而且只有 1 个变体。建议扩变体而不是新增槽位。

我把 `1.16.5-Forge_36.2.34.jar` 拆开看了（14646 个条目，882 个 `.nbt`）：

| 玩家想要 | MC 里的实现 | 我们的路子 |
|---|---|---|
| 沉船 | `data/minecraft/structures/shipwreck/*.nbt` **20 个** | 可用 `tools/convert_nbt.py` 直接转，一次拿到 20 个姿态（正放/侧翻/倒扣/带桅杆/断成两截） |
| 海底废墟（附赠） | `underwater_ruin/*.nbt` **48 个** | 极便宜的海底内容量，冷/暖两套 |
| 海底神殿 | **代码生成，无 nbt** | 需手写 builder（58×58×23） |
| 丛林神庙 | **代码生成，无 nbt** | 需手写 builder（约 12×15×12） |
| 沙漠神殿 | **代码生成，无 nbt** | 需手写 builder（21×21 金字塔） |

好消息是那三个「没有 nbt」的，SC 侧元件全都有，能做得相当还原
（下列方块名都在 `Assets/BlocksData.txt` 里核对过）。
**精确尺寸与坐标见下面第 3.5 节 —— 已从 1.16.5 原版生成器反编译得到，不是估算值。**

- **沙漠神殿**：`SandstoneBlock` / `SandstoneStairsBlock` / `SandstoneSlabBlock` 砌金字塔；
  地下密室 4 箱围一圈，中心 `PressurePlateBlock` + `WireBlock` + `DetonatorBlock`
  + `LargeGunpowderKegBlock` —— MC 的 TNT 陷阱可以 1:1 复刻。
- **丛林神庙**：`CobblestoneBlock` + `IvyBlock` 做苔石感；
  `DispenserBlock`（装箭）+ `PressurePlateBlock` + `WireThroughCobblestoneBlock` 复刻绊线射箭陷阱；
  `SwitchBlock` ×3 复刻拉杆解谜开暗门。SC 的电路系统完全够用。
- **海底神殿**：`MarbleBlock`（白）/ `GraniteBlock` / `BasaltBlock` / `FramedGlassBlock` 拼海晶石观感，
  `WickerLampBlock` 当光源；核心藏 `TreasureGeneratorBlock` + 金锭箱；
  守卫用 `Shark_Tiger` / `Barracuda` / `Piranha` 群。
  设计要点：MC 那套「远古守卫者挖掘疲劳」没法复刻，改用**氧气压力**——
  内部只留少量气室，宝库需要连续下潜 + 挖开封层，天然形成难度。

#### 海底神殿 `OceanMonumentPieces`（58 × 23 × 58，y=39..61）

不是一整块死板结构，而是「固定外壳 + 随机房间图」：

- **外壳**：58×58 底面，高 23（MC 里 y 39→61，顶部刚好在海平面 64 下方）。
- **基座柱**：7×7 网格，每个格点一根 4×4 的柱子，间距 9 格（`n*9`），从 y=0 向下
  `fillColumnDown` 打到海床——这就是它能立在任何深度海底的原因，**这个手法我们直接抄，
  正好解决 SC 海床起伏问题**。
- **两侧翼**：`(1,1,1)–(23,8,21)` 与 `(34,1,1)–(56,8,21)`。
- **顶阁**：`(22,13,22)–(35,17,35)`。
- **房间网格**：5(x) × 3(y) × 5(z) 的槽位，索引 `index = y*25 + z*5 + x`；
  每个槽位实际尺寸 **8×4×8**（`sizeX*8-1, sizeY*4-1, sizeZ*8-1`）。
  第 0、1 层各 5×4 个房间，第 2 层只有中间 3×2 个。
- **随机化**：房间之间按六向连通建图，随机洗牌后为每个房间尝试开 2 个门（`findSource`
  保证仍与入口连通），再用 7 种房间原型按优先级匹配填充：
  `双XY / 双YZ / 双Z / 双X / 双Y / 简单顶层 / 简单房`。
  **这套「网格 + 连通性约束 + 原型匹配」的做法值得整套借鉴**，比我们现在的固定模板耐逛得多。
- **核心宝库**：入口房固定在 `getRoomIndex(2,0,0)`；核心房随机取 `getRoomIndex(rand(4),0,2)`，
  并连带占用它东/北/上共 8 个格位（即 2×2×2 大房）。宝库内部：
  `(6,3,6)–(9,6,9)` 深色海晶石外壳，**`(7,4,7)–(8,5,8)` = 8 个金块**，四角海晶灯。

### 前置改造：`PlacementEngine` 目前没有生物群系过滤

沙漠神殿/丛林神庙必须挑群系，而现在 `AnchorKind` 只看高度和坡度。
好在 `ITerrainContentsGenerator` 暴露了 `CalculateTemperature(x,z)` 和 `CalculateHumidity(x,z)`（都是 0~15），
`IWorldSampler` 加两个方法即可，`StructureDef` 加一个可选 `BiomeFilter { TempMin/Max, HumidityMin/Max }`。
参考原版判据（`TerrainContentsGenerator24.cs:732` 沙地条件是 `温度>8 && 湿度<8`）：
沙漠取 `温度≥10 && 湿度≤4`，丛林取 `温度≥10 && 湿度≥11`。
这个过滤器做好以后，现有结构也能顺手调（比如渔屋别再刷到冰原）。

### 前置改造 2：待填容器管线要泛化

丛林神庙的两个发射器必须装箭，否则陷阱是哑弹。SC 的 `ComponentDispenser` 继承
`ComponentInventoryBase`（与 `ComponentChest` 同一基类），所以 `RuinsRuntime.FillChest` 里
那套「建 BlockEntity → `AcquireItems`」的逻辑可以原样复用，只需把 `PendingChest`
泛化成 `PendingContainer { X,Y,Z, EntityTemplate("Chest"/"Dispenser"), Pool, Seed }`，
`WorldState.WriteInstancePart` 里识别 `DispenserBlock` 时一并入队。
存档 JSON 字段随之变化 —— 要么加版本号做迁移，要么并入 v0.5.0 的存档格式改动一次做完。

### 一个需要你确认的事项

`tools/convert_nbt.py` / `assemble_wda.py` 说明现在的 sky_fortress、coliseum 等模板是从
When Dungeons Arise 的结构文件转过来的。如果继续走「转 MC 原版 nbt」这条路，
分发的是 Mojang 资产的衍生几何数据，AGPL 包里带着风险高于 WDA。
建议：**海底神殿/丛林神庙/沙漠神殿反正没有 nbt，本来就要手写 builder，零风险**；
沉船/海底废墟如果也想要，优先自己写程序化生成器（沉船已有一个，扩几个姿态不难），
把 nbt 转换留作本地参考而不是发布内容。这一条你自己拍板，我按你的决定做。

## 六、实现记录（v0.5.0 实际落地）

三个阶段一次做完，`dotnet test` 49 项全绿。

### 密度

| 指标 | 改前 | 改后（实测） |
|---|---|---|
| 陆地结构密度 | 98 个/km² | **26.8 个/km²** |
| 平均最近邻距离 | ~50 格 | **~97 格** |

- 网格按方案表重标定（`small` 7→14 格、`grand` 24→40 格等），未压 `Chance`。
- 同槽间距：原点抖动限制在格子中央 50%（`PlacementEngine.ComputeInstance`），
  相邻格子实例硬性隔开约四分之一格。测试断言相邻格子间隙 ≥100 格。
- 跨槽间距：`StructureDef.SeparationRadius`（40~160）在重叠抑制循环里按中心距判定，
  只查更高优先级槽位，无递归风险。
- `PlacementEngine` 接受 `densityScale`；0=不生成，实测 0.5 < 1.0 的数量。

### 守卫

预算制落在 `Core/GuardPlanner.cs`（纯逻辑、可测），`WorldState` 只负责缓存与入队。

### 新结构

- `DesertTempleBuilder` 21×21×15、`JungleTempleBuilder` 12×15×10、
  `OceanMonumentBuilder` 58×58×44（含 26 格基座柱），坐标全部照 3.5 节的反编译结果。
- 生物群系过滤（`BiomeFilter` + `IWorldSampler.Temperature/Humidity`）已接通，

- 新增战利品池 5 个：`desert_temple` `jungle_temple` `trap_arrows`
  `monument_wing` `monument_vault`。

### 与方案的差异

1. **海底神殿内部不写方块**。原方案没提；实现时发现如果把房间内部填成空气，
   水下神殿会变成干燥洞窟。改成只写墙体、让海水留在原处，顺带把单实例从
   约 77k 格降到 **29.5k 格**（建造耗时 38 ms）。空气只写在两翼屋顶下的换气室。
2. **新增 `StructureVariant.Bounds`**。`PlacementEngine` 原本先建结构再判定锚点，
   对 58 格的神殿意味着每个候选格子都要白建一次。现在声明了尺寸的变体先判定后建造。
   测试 `MonumentBoundsMatchWhatItBuilds` 保证声明值不漂——它在开发中真的抓到了
   一次（顶阁比主屋顶高一格）。
3. **老世界钉在 layout 1**，代价是它们拿不到三座新神殿（换开新世界）。
   这比让老世界边缘留下半截建筑更可接受。
4. **MC 的绊线钩/红石粉在 SC 没有对应物**，改用压力板 + 电线面位掩码；
   丛林神庙西侧发射器改为朝走廊(+Z)而非原版的北向，否则会对着墙射。
5. **陶瓦用上色砂岩代替**——SC 的 `SandstoneBlock` 是 `PaintedCubeBlock`，
   调色板 6 号≈橙、11 号≈蓝，地板拼花因此能一格不差地还原。

## 七、v0.6.0：实机测试后的第二轮修正

0.5.0 交给玩家实测后的反馈：小建筑变少了、三座神殿一座没见到、守卫刷在
不相干的位置。前两条在 0.5.x 里靠调网格试了一轮仍然没解决，于是改为**离线复现
真实世界**来定位——把 `TerrainContentsGenerator24` 的 `CalculateHeight` /
`CalculateTemperature` / `CalculateHumidity` 连同种子偏移(`Random(seed)` 的前四次
`Float(-3000,3000)`)在 scratchpad 里原样重写，直接对玩家的真实种子跑 `PlacementEngine`。

### 定位到的真因：单点选址

| 种子(36 km² 范围内) | 0.5 布局 | 0.6 布局 |
|---|---|---|
| 陆地结构合计 | 166~192 | 168~206 |
| 沙漠神殿 | **0~1 座** | **3~10 座** |
| 丛林神庙 | 1~3 座 | 9~16 座 |
| 小建筑(`small`) | 61~70 | 37~65 |

0.5 的表是在平坦测试世界上标定的：每个格子只取一个抖动落点，命中就生成、
不中就整格作废。真实地形里这一点很可能落在海里或坡上——实测按 40 个/km² 标定的表
实际只落地 19.7 个/km²，而带群系过滤的沙漠神殿更是被连乘到近乎归零
(0.5 概率 × 14% 群系 × 26% 是陆地 × ~26% 够平 ≈ 0.5%/格)。

修正是 `PlacementEngine.DefaultSiteAttempts = 8`：格内按确定性序列试最多 8 个落点，
第一个通过群系/坡度/水深的胜出。密度上限(每格最多一个)和中央 50% 抖动的间距保证
都不变，但表上的数字终于等于实际密度。因此网格同步放宽(`small` 10→18、
`tower` 17→25、`den` 22→30 等),让"稍微再少一点"的要求和密度修正同时成立。

耗时实测:暖缓存下每区块 0.045 ms → 0.146 ms，相对地形生成可忽略。

### 群系判据

用户问"温度湿度准不准、SC 有没有群系"——SC 没有群系对象，温度/湿度两张噪声图
就是它的全部群系系统。但顺手核对了游戏自己的用法：地表沙子来自砂岩地层裸露
(`GenerateSurface` 判 `num5 == 4`)，跟湿度无关；真正由湿度决定的是植被——
`PlantsManager.CalculateTreeProbability` 里橡树在湿度≤6 概率为 0、云杉在温度≥10 为 0。
所以沙漠判据放宽到 **温度≥9 且湿度≤6**（占全图 13.7%、其中陆地 3.6%），
既多出 17% 的可选面积，又仍然保证落在无树干热带。

### 守卫

`GuardPlanner` 改为**只用宝箱位置作守卫点**，模板自带的埋伏标记退化为"结构一个箱子
都没有"时的兜底——那些标记是从 WDA 原结构导入的刷怪点，会把守卫撒在没有战利品的
房间。`RuinsRuntime.FindSpawnY` 同时改成以标记高度为中心上下各找 6 格，避免地窖里的
守卫被顶到屋顶。

### 存档兼容

`CurrentLayoutVersion = 3`，并新增 `s_layout2` 表：0.5 世界保留原网格且
`SiteAttemptsFor(2) == 1`，0.5 之前的世界仍走 layout 1。老世界不会因为升级而在
已探索边缘留下半截建筑，代价是拿不到新密度——神殿要好找必须开新世界。

## 八、v0.6.1：三处陷阱电路是断的（实机反馈）

玩家报告"丛林神庙的发射器不会被触发、沙漠神殿的压力板不会引爆炸药"。查 SC 源码后
确认机制本身没问题——生成时写进区块的电元件**会**被注册:`TerrainUpdater` 在
`NotifyBlockBehaviors` 里逐格调 `OnBlockGenerated`,`SubsystemElectricBlockBehavior`
(HandledBlocks 含 133 电线 / 144 压力板 / 147 起爆器 / 154 穿石电线 / 216 发射器 /
237 活塞 / 106 火药桶)转给 `SubsystemElectricity.OnElectricElementBlockGenerated`。
我们的 `OnTerrainContentsGenerated` 钩子跑在 `InvalidContents4`,早于该扫描,所以
结构里的电元件全都进了电路系统。

问题出在接线本身。为了不再靠肉眼推断,把游戏的接线规则整套移植进了测试:
`tests/SurvivalcraftRuins.Tests/ElectricModel.cs` = `m_connectionPathsTable`(120 项,
直接从反编译源码脚本生成后逐项比对)+ `m_connectorDirectionsTable`(36 项,等价于
"接口面 == 挂载面时无效")+ 每个方块的 `GetConnectorType` + `WireBlock` 的同格面
合并规则 + `ScanWireDomain` 的连通语义。跑 0.5 的产物,结论是**每个元件各自一个
连通分量,一处都没接上**。

三处根因：

1. **丛林西侧陷阱**:压力板在 (2/3,-3,8),电线从 x=5 起步——中间隔着两格,而且
   x=5、z=6~7 那几格本来是实心墙(等于在墙里挖了条带电线的洞)。
2. **丛林东侧陷阱**:同类问题,电线绕在 (8~9,-3,4~6),没有一格与压力板相邻。
3. **沙漠神殿**:压力板→穿石电线这一段其实是通的(挂载面 4 的 `In` 路径正好指向
   正下方,穿石电线竖直导通),断在最后一步——`DetonatorBlock.GetFace(data) = data & 7`,
   我们写的 data 0 表示挂载面 0(+Z),它只从 +Z 侧收信号,而信号从正上方来。
   改成 data 5(吊在上方电线块下面)后 `In` 路径 (0,+1,0) 正好对上。

顺带发现丛林神庙的暗室(x8~10,z8~10)**根本没有入口**——四条基础走廊都不通到那里,
第二个箱子在 0.5 里是拿不到的。重做为 1 格宽的壁龛 + 墙内活塞门:活塞(x=7)、
臂位(x=8)、塞块(x=9)、凹槽(x=10),都埋在 z=11 的墙里;壁龛只有 1 格宽是必须的,
否则塞块的凹槽会顺带开出一条绕过门的通路。塞块用普通圆石,活塞万一不动也能挖开。

三根拉杆改为"只有一根通电"(按实例种子挑),另两根是幌子——SC 没有现成的组合锁,
与其做一套门电路不如把不确定性降到零。

回归测试:`TrapTests` 断言每块压力板与对应发射器同电路、发射器处于射击模式且面前
不是实心墙、每根电线都贴着实心方块、三根拉杆里恰好一根与两台活塞同电路。

## 九、v0.7.0：守卫踩雷、老世界、活塞门看不懂

### 守卫别站在触发器上

`GuardPlanner` 从 0.5 起把守卫点一律钉在宝箱上,这在普通遗迹里是对的,但两座神殿的
箱子恰好就围在陷阱触发器旁边——美洲豹在密室里踱两步就踩响压力板,玩家还没下去
火药就炸了。新增 `GuardSpec.PostsAtMarkers`:置位时改用结构自己声明的埋伏标记
(沙漠=入口大厅三处、丛林=上层主厅三处),预算仍按箱子数算。`TrapTests` 加断言:
任何守卫岗位与任何压力板必须差 ≥2 层楼或水平 >4 格。

### 老世界可以直接装

原来的"布局冻结"是为了避免已探索边界出现半截建筑,代价却是**玩家给自己在玩的存档
装上模组后拿不到任何新内容**——这是本末倒置。取消冻结:删掉 `s_layout2` /
`s_legacyLayout` / `ApplyLegacyLayout` / `SiteAttemptsFor`,`CreateDefs` 不再收
`layoutVersion`,所有世界一律用当前表,`Density`/`Guards` 设置也随时生效。
`LayoutVersion` 仍写进存档,只作诊断;载入时若与当前值不同会打一行日志。
残留风险仅剩:已生成土地的边界上、且新旧布局不一致处,可能有一处写了一半的建筑。

### 活塞门要能看懂

玩家反馈"不知道活塞是干嘛的"。原设计三根拉杆在走廊一侧、活塞门在另一侧,但门板与
周围墙同为圆石,读不出"这是门"。改动:门板换成石砖并加过梁,与苔石墙形成对比;
拉错的那根杆接到墙里的发射器,会射一箭——错误选择也有反馈,玩家立刻明白三根杆在
控制什么。三根杆的分工(开门/放箭/无效)按实例种子分配,`TrapTests` 断言放箭那根
与门电路不属于同一连通分量(否则拉错也会开门)。
